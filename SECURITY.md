# Security Policy

## Reporting a vulnerability

**Please do not open a public issue for security vulnerabilities.**

Report privately through GitHub's
[private vulnerability reporting](https://github.com/karanmjpinto/mjresearch/security/advisories/new)
form. If that is unavailable, email **karanmjpinto@gmail.com** with `SECURITY` in the
subject line.

Please include:

- what the issue is and roughly how bad you think it is,
- the steps or request needed to reproduce it,
- the version or commit you tested against.

This is a personal project maintained in spare time, so please expect an initial reply
within about a week rather than within hours. You will get credit in the fix unless you
would rather not.

## Scope

This project is designed to run **on your own machine, bound to localhost**. Please read
the threat model below before reporting.

### In scope

- Remote code execution, path traversal, or SQL injection reachable through the API.
- A dependency vulnerability that is actually exploitable through this codebase.
- Secrets leaking into logs, run records, snapshots, or the built frontend bundle.
- Prompt injection through fetched market data or SEC filings that causes the harness to
  report an unverified number as verified.

### Out of scope

These are known and intentional properties of a localhost-only tool, not vulnerabilities:

- **The API has no authentication.** Anyone who can reach the port has full read and
  write access to the portfolio, including the trade endpoints. This is why the backend
  is deliberately not hosted, and why exposing it to the public internet is unsupported.
- **The SQLite book is unencrypted.** It is a file you own on a machine you control.
- **Third-party market data can be wrong or stale.** Provenance records which provider
  answered; it does not attest that the provider was correct.

If you deploy this somewhere reachable from the internet, you are outside the supported
configuration and the first two points become your problem to solve.

## A word on the output

The research output is generated by a language model and can be wrong in ways that read
perfectly plausibly. Incorrect analysis is a **correctness bug**, not a security
vulnerability — please report it as a normal issue, ideally with the run id.
